# The 3D renderer

This page describes how UW2 draws the 3D view: the C that turns the map around the player into a program for the renderer (`src/3d/*.C`), and the assembly renderer that runs that program (`src/3d/*.ASM`, DOS segment seg004, entered through seg021). The declarations are in `src/include/view3d.h`. Statements marked "probably" are inferences; the reason is given with each.

## Files

| File | Segment | Name | What it does |
|---|---|---|---|
| `VIEW3D.C` | seg032 | descriptive | places the view, sets up a frame, builds the vision grid, runs the renderer and shows the frame |
| `GRIDDB.C` | seg019 | descriptive | turns the vision grid into render-database bytecode, tile by tile; marks the automap |
| `SETPNT.ASM` | seg019 | descriptive (its routine's own name) | `SetPnt`, which appends one point to the database; linked into GRIDDB.C's code segment |
| `GAMESORT.C` | seg034 | inferred (System Shock's `GAMESORT.C` has the same job) | orders each tile's objects for drawing |
| `DRAWOBJ.C` | seg033 | descriptive | emits one object: a sprite, a critter frame, a 3D model or a door |
| `EXPAND.ASM` .. `PGCACHE.ASM` | seg004 | see below | the renderer, 14 modules of one library |

Function and global names in the C are the originals from the FM Towns symbol table where it has them. `map/filenames.tsv` has the evidence for each file name.

## A frame

1. The main loop calls `establish_view` (VIEW3D.C) through `do_3d_view` (game/UWEDIT.C). `render_FB` does the same but leaves the picture in the frame buffer, for fades and screens drawn over the view.
2. `setup_vars` has `get_eye` copy the player's position into the camera, `cPlayer` (`struct Camera`). It then turns the camera into the first quadrant: the heading's octant picks a quadrant `quad`, the camera's position within its tile is rotated to match, and the quadrant's quarter turn is taken off the heading. From here on the C walks the map as if the player always faced the same way; `chgtable` turns a step along the view's x, y or diagonal into a map index step, and `trans_grid` turns tile types (the slopes and diagonals have a direction) to match.
3. `do_2dclip` builds the vision grid (`init_grid`, `build_grid`) and calls GRIDDB.C's `process_grid`, which writes the frame's bytecode.
4. `send_db` sets the clip window to the view and calls seg021's `cRender`, which runs the bytecode into the frame buffer; `cFBtoScreen` copies the frame buffer to the screen with the mouse cursor hidden.

`cRender` (src/sys/C3DENTRY.ASM) switches to the private stack in seg021's data segment (FD71, `dseg062_62a6`), notes the tick count, installs the renderer's divide-by-zero handler for the duration (int 21h function 25h, vector 0) and calls, in turn, seg003's `clear_fbuf` (`seg003_0272_6E2`, GRENTRY.ASM), `render_3d` (INSTANCE.ASM), seg003's frame-time stamp (`seg003_0272_18`, GRMISC.ASM) and `update_cache` (PGCACHE.ASM). It restores the stack and the vector and returns the ticks the frame took. The picture is drawn into a linear frame buffer, not the screen; `cFBtoScreen` copies it to the mode X screen afterwards.

## The vision grid

`glocs` (VIEW3D.C) is 17 rows of 33 cells, one per tile: row 0 is the eye's row and column 16 the eye's column, rows going away from the eye in the turned frame. Each cell is a `struct Gloc` (view3d.h): a flags byte (0x80 seen, 0x04 a slope, 0x44 a diagonal, the low two bits which one, and 0x20, 0x10, 0x08 the three walls that may show) and a shade byte (the distance shade in bits 0-3, 15 meaning too far; bits 4-6 say that the neighbour behind each wall is not solid, so the wall runs up to the neighbour's floor instead of the ceiling).

`preset_grid` fills each cell's distance shade once (from `init_3d`, range 8), from the distance to the eye scaled by the renderer's `smooth_div`, `smooth_lowpass` and `smooth_base`.

`init_grid` starts two edges (`struct Gvec`, a list in `gvecs` headed by `gvechead`) at the eye, aimed at the heading -0x2040 and +0x2040 (a full turn is 0x10000). `build_grid` moves the edges out row by row: `move_to_next` walks an edge across its row and stops it at side walls, `newdels` moves both edges to the next row and re-aims them through their new points, and `fill_the_grid` marks every cell between a pair of edges with `enc_n_chk`, which looks the tile type up in `enc_dat` (the faces a tile shows from each of seven directions) and drops the walls hidden by a neighbour at least as high. Where a wall splits a span the edges are split too. Cells outside every span get flags 0. `mxY` is the farthest row reached.

## The render database

The render database is a buffer of the model interpreter's bytecode, written through `dbptr`. The label code that goes with it is in `src/conv/GRDB.C` (`grdb_blank`, `Ref`, `gr_putlab`, `Clk`; it is the same assembler the conversation code uses), and the 3D models' own bytecode lives in the renderer's far data, with their label positions in a table just before the database buffer (labels 96 to 159). `init_3d` writes a 0 word at the entry (`DbEntry`) and each frame starts there again (`reset_db`). A frame's code ends with label 0xA0 and a 0 word (`do_eof`).

The opcode numbers are those of seg004's opcode table at 4FAF:24F4, which has the same handlers in the same order as FM Towns' opcodes (docs/LAYOUT.md; UWReverseEngineering's `UW2 FM Towns/model_opcodes.tsv` lists them). The handler names say what most of them do. The ones the C emits:

| Opcode | Handler | Emitted by |
|---|---|---|
| 0x02 | `do_movec`: store a constant in a model variable (`Clk(n)` is the variable's address) | everywhere |
| 0x12, 0x50 | `do_sfcal`, `do_ihcall`: call a model, unturned or turned by a heading | `do_rect` |
| 0x18 | `do_org`: set the origin (three longs) | `do_rect` |
| 0x2E, 0x7E | `do_setcolor`, `do_polyres`: a flat polygon | GRIDDB.C's `poly*` |
| 0x36, 0xA0, 0xA2 | `do_tmap`, `do_compact_tmap`, `do_compact_wtmap`: a texture-mapped face | `txtflr`, `txtwal` |
| 0x38 | `do_obj` | the frame header |
| 0x3A | `do_uwobj`: a sprite object | `do_obj` |
| 0x3E | `do_fetchmap`: load a texture into a bitmap slot | `txtflr`, `txtwal` |
| 0x4C | `do_defdelta` | `do_rect`, `do_door` |
| 0x5A | `do_uwcrit`: a critter frame | `do_obj` |
| 0x7A | `do_defres`: define a point | `do_obj` |
| 0xAE | `do_setbmcol`: the pick colour | pick frames |
| 0xB0 | `do_mouseq` | the end of each grid row |
| 0xB2, 0xC0 | `do_set_tmctxt`, `do_settmobj`: texture context for a model | `do_obj`, `do_rect`, `do_door` |
| 0xB6 | `do_minires`: a point record | `SetPnt` |
| 0xD0 | `do_set_gmap_ctxt` | the frame header |

`do_mouseq` at the end of each row lets the mouse cursor be serviced while a frame renders: the handler (PGCACHE.ASM) far-calls seg021's `seg021_22FD_102B` (C3DENTRY.ASM), which saves the renderer's stack, runs the C routine `MousQUp(1)` on a small DGROUP stack and restores the stack; FM Towns' `do_mouseq` calls `MousQUp(1)` directly.

### Tiles

`process_grid` writes a frame header (an object call at label 0xA0 and model variables 9, 8 and 4) and calls `subprocess`, which walks the grid from row `mxY` down to the eye's row. Each row is walked from the left edge to the middle, then from the right edge to the middle, then the middle column, so nearer faces come later in the database and are drawn over farther ones. `grdb_elem` emits one tile: the floor (when the eye is above it, or a slope's facing side), the ceiling (when the eye is below 0x3F4 and the level has ceilings), each wall the grid marks, the diagonal face, then the tile's objects. Points come from `SetPnt` (x, y the grid cell, z a tile height, 16 the ceiling).

Each face is drawn flat or texture mapped through the function pointers `gr_fcall`, `gr_ccall` and `gr_wcall`, chosen from `gftab`, `gctab` and `gwtab` by `tmapson`. `set_graphics_level` sets them from the detail setting: 0 no texture mapping, 1 walls, 2 walls and floors, 3 walls, floors and ceilings. Beyond distance shade `distpoly` (7) textured faces fall back to flat ones. A flat face uses the texture's average colour (`TxmCol`, map/TEXTMAPS.C) through the light tables `cLightTabs`.

On levels 65 to 72 other than 68 the frame is drawn with no ceiling and no distance lighting (probably a world whose levels are open or unlit; not checked against the game).

### Automap and experience

`grdb_elem` also maintains the automap (`PlayersMap`): every tile the walk passes gets an automap code (its tile type, its floor's terrain class, and `curautocode` in the high nibble for doors and textured objects). Tiles that were unmapped count in `pipeexp`, and after the frame `process_grid` gives experience for them, `pipeexp * (PlayerLevel / 8 + 1) / 10`, while the character's level is 1 to 15.

### Objects

For each tile `grdb_elem` passes the object list to GAMESORT.C's `do_objsort`. It computes each object's position within the tile in the turned frame (`set_sds`), a sort key for the part of the row being drawn (`set_osum`), and sorts farthest first; a tile with a door or bridge is first split around it (`do_partition`, `door_part`, `z_part`). Animated objects that reach over the edge of their tile are held back (`refugees`, `holdmid`, `holdtmp`) and drawn with the neighbouring tile that is drawn later, so the neighbour's faces do not cover them. Each object then gets its view position (`objxloc`, `objyloc`, `objzloc`) and distance shade (`locsqmod`) and goes to DRAWOBJ.C's `do_obj`.

`do_obj` draws by the render field of the object's COMOBJ.DAT entry: 0 a sprite (`do_uwobj`), 1 a critter (`do_uwcrit`, its frame looked up in the critter's art page through `grs_3dinf` and the frame table in the EMS page frame), 2 a 3D model (`do_rect`, the model from `rect_sub`) or a door (`do_door`), 3 a texture-mapped object. `do_rect` sets the model's colours and texture in model variables (from `rect_cols`), sets the origin and calls the model's code at label 0x60 + model. A few models are special-cased: model 0x1E lights a face for each blackrock gem used (quest byte 130; probably the large gem), and model 0x1D takes its colours from the object.

### Pick frames

To find what the cursor is on, UI/INTERACT.C's `pick_3d` calls `do_3d_grab`, which renders a frame with `do_3d_pickup` in place of `process_grid` and does not show it. In a pick frame every face and object is drawn flat in a colour that identifies it: floors 0xEC + texture, walls 0xAC + texture, ceilings 0xFC, and objects 1 to 0xAB, each recorded in `color_to_obj` with its tile in `color_to_map`. `pick_3d` reads the byte under the cursor and looks it up. The pick frame reuses the vision grid of the last normal frame.

### The hallucination effect

`set_cyb` (VIEW3D.C) writes random values into word 1 of the first six bitmap-table slots, and puts back 0xF0, 0xF0, 0x3E0, 0x3E0, 0xFC0, 0xFC0 when it is turned off. PLAYDATA.C uses it as one of three random effects while the player is affected by mushrooms (`ShroomsEnabled`). The words are probably the texture-coordinate masks, so the textures scramble; this has not been checked in seg004.

## Key structures

- `struct Camera` (view3d.h): the camera `cPlayer`, with x, y and z in 1/256 tile and pitch, bank and heading.
- `struct Gloc` (view3d.h): a vision-grid cell, as above.
- `struct Gvec` (VIEW3D.C, file-local): an edge of the vision arc.
- `struct Grs3d` (view3d.h): the art page of each 3D object type's pictures.
- `struct Tile` (map.h): the map tile the grid walk reads (type, height, floor and wall textures, object list).
- `rect_cols`, `rect_sub` (DRAWOBJ.C): the 3D models' colours and the model for each object type.

## The seg004 renderer modules

seg004 was a library of 14 assembly modules, split by the zero padding TLINK put between them ([LINKING.md](../LINKING.md#the-exact-link)). seg021's C entry points (`cRender`, `cInit3d`, `cZoom`, `cPlaceFB`, `cFBtoScreen`, `cSinCos`, `cSqRt` and others, src/sys/C3DENTRY.ASM) switch to seg021's private stack and call into it. Its data is the far segment `seg052_519C` (FD58), partly defined by TMAPOPS.ASM and partly taken from the EXE; every routine runs with DS on it.

| Module | Name | Contents |
|---|---|---|
| `EXPAND.ASM` | descriptive | the image decoders `exp_8str`, `exp_4str`, `exp_4run`, `exp_5run`, `exp_8run` and `uncmp_pal`: a .GR or .CR picture to one byte per pixel through its auxiliary palette, optionally shaded |
| `SPHERE.ASM` | descriptive | `do_obj` (opcode 38h, the header of each placed thing: origin, shift, and the bounding-sphere cull `sphere_check`), `get_dist` |
| `SMOOTH.ASM` | descriptive | `smooth_closure`: Gouraud polygons, projected and clipped with a shade per vertex, handed to seg003's smooth polygon (GRLIBM.ASM) |
| `INTERP.ASM` | original (System Shock's `interp.asm` has 17 of its opcode handlers) | the model interpreter: the opcode table, the matrix set-up, and the handlers `do_int2` .. `do_movres` with their `flat_` variants |
| `INSTANCE.ASM` | inferred (System Shock's `instance.asm`) | `render_3d`, the view matrix (`scale_matrix`, `check_flat`), point transforms (`mxmul`), clip codes (`code_pnt`), the `instance_` rotations, 3 x 3 products, the divide-overflow handlers |
| `TMAPOPS.ASM` | descriptive | the texture-mapping opcodes `do_set_tmctxt` .. `do_tmap`, `draw_solid_tmap`, and `do_scalebm` (sprites); the start of FD58's defined data |
| `CLIP.ASM` | inferred (System Shock's `clip.c`) | `_asm_clip_polygon`: Sutherland-Hodgman against the four 45-degree planes |
| `PERTLP.ASM`, `PERTP.ASM` | descriptive | the four horizontal span drawers: perspective or linear, shaded or not |
| `PROJPOLY.ASM` | descriptive | `asm_texture_map_from_draw_poly` (chooses perspective or linear, horizontal or vertical), `_asm_project_polygon`, `compute_lighting_value` |
| `SCANLINE.ASM` | descriptive | the vertical span drawer for walls (probably FM Towns' `_asm_texture_map_scanline_lin_tlpv`) |
| `TEXMAP.ASM` | descriptive | `_asm_texture_map`: the polygon filled row by row |
| `TEXMAPV.ASM` | descriptive | `_asm_texture_map_v`: the polygon filled column by column, for walls |
| `PGCACHE.ASM` | descriptive | the art opcodes `do_fetchmap`, `do_settmobj`, `do_uwobj`, `do_uwcrit`, `do_uwcolv`, `do_setbmcol`, `do_mouseq`; the critter page cache (`load_cpg` .. `update_cache`); `uncmp_tab` and `lightabs` |

### The interpreter

The render database and the 3D models are one bytecode (INTERP.ASM's header has the details). An opcode is an even word, the offset of its handler in the table at FD58:24F4; every handler ends by fetching the next word and jumping through the table, so there is no central loop, and `do_eof`'s `ret` ends a program or sub-program. Points are transformed into view space as they are defined (`mxmul`, with the eye position patched into the code by `self_modify`) and kept in the point table at 14D0, 8 bytes each with their clip codes (`code_pnt`: one bit per frustum plane, 80h behind the eye). Sub-objects are drawn under a rotation by heading, pitch or bank (`instance_head` and the rest), with the matrix saved and restored around them. While the view is level, `check_flat` swaps in cheaper handlers and a cheaper `mxmul`, since the vertical axis does not mix with the others.

### Polygons

A flat polygon is projected, clipped in 3D if its codes require (INTERP.ASM's `clip_top` and the rest) and passed to seg003's polygon routines with the vertices at `seg_370D:415E`; a Gouraud polygon goes through SMOOTH.ASM to seg003's `spolygon` (GRLIBM.ASM), which writes spans for GRENTRY.ASM's `vga_smooth_ylrii`. Its shading is lightabs rows chosen per pixel and dithered between neighbouring rows.

A textured polygon is collected by a TMAPOPS opcode (12-byte vertices with texture coordinates), then `asm_texture_map_from_draw_poly` (PROJPOLY.ASM) turns it into 32-byte 16.16 records, chooses perspective or linear mapping by the spread of depths, and vertical columns for the wall opcodes; `_asm_texture_map_1` clips it (CLIP.ASM), projects it and gives each vertex its distance shade, and calls `_asm_texture_map` (TEXMAP.ASM) or `_asm_texture_map_v` (TEXMAPV.ASM). Those walk the polygon's edges and call a span drawer for each row or column; the drawers read the texture through `GS`, shade texels through `lightabs` (dithered by pixel parity) and write the frame buffer. Floors and ceilings (while the view is level) get exact perspective at both ends of every row and are drawn linearly between (each row is at one depth), and upright walls the same down each column, so only polygons at other angles need the per-pixel perspective drawers. A divide overflow anywhere abandons the polygon.

If texture mapping is off (`polym`), `draw_solid_tmap` draws the same polygon flat.

### Sprites and critters

Objects drawn as pictures go through `do_uwobj` (an object's picture from the art in EMS, slot from `obj_tab`) or `do_uwcrit` (a critter's animation frame), which decode the picture with EXPAND.ASM into a buffer and hand it to TMAPOPS.ASM's `in_scalebm`. That projects the sprite's corners and calls seg003's `scale_nibble_bitmap` (SCALEBM.ASM), which draws it scaled into the frame buffer with a scaler generated as code for each sprite's width.

Critter frames are paged: each critter's animations are files `CRIT\CRnn.0p` (nn the critter's map number in octal, p a page). PGCACHE.ASM keeps the pages in an EMS cache of 32 KB slots, loads a page from disk when a frame needs it, ages every page each frame (`update_cache`) and throws out the least recently used when it needs a slot.

### Orientation

seg003's screen coordinates count y up from the bottom line (VIDMODE.ASM builds its row table that way), and so does the frame buffer, whose last row `cFBtoScreen` copies to the top of the screen. The view's window, set with seg003's `set_the_window`, is copied to FD71:0C30, where `render_3d` reads it to set the projection's scale and centre.

## Open questions

[FINDINGS.md](../FINDINGS.md) collects the open questions and likely bugs of every subsystem in one place.

- Which world levels 65 to 72 (less 68) are, and why they are drawn with no ceiling and no lighting.
- What `do_set_gmap_ctxt`, `do_defdelta` and the frame header's model variables 4, 8 and 9 do exactly; the C only shows how they are used. (`do_set_gmap_ctxt` sets which mapping, floor or wall style, the context-textured opcodes use.)
- `seg032_2E9B_18B` and `seg032_2E9B_195` have no callers and no FM Towns counterpart; the second toggles `SpecShadeMode` and points bitmap slots 1, 3 and 5 at the 4 KB buffer `seg_5DFD`, for a reason not yet known.
- Whether the words `set_cyb` overwrites are the texture masks. Word 1 of a bitmap slot is the v extent the compact and fractional texture opcodes scale by (TMAPOPS.ASM), so random values there would stretch the textures in v; not checked in the game.
- `do_fetchmap` sets `tmcolor` from the wrong segment in DOS (it loads DS from SI where FM Towns reads the texture), so the value is not the texture's first pixel; what reads `tmcolor` has not been traced.
- `do_bcompact_map` uses whatever AX the previous handler left as its texture block, where FM Towns loads `bmap_blk_ptr`; probably the C never emits it.
- `mm3x9_bpsi` and `mm3x9t` saturate the second product instead of the third when the third overflows (FM Towns saturates the third). Overflow there is probably rare.
- POLYFILL.ASM's wall mapper, at the address seg004 keeps as `mapper_rtn` for walls, is never called in DOS; the vertical texture mapper replaced it.
- `do_door`'s choice of drawing order (frame or leaf first) is read from the code, but the geometric meaning of its test has not been worked through.
